### 2. 遇到的问题与解决过程

#### 问题一：活期按日计息的"起算点"缺失，重复结息会重复计息
- **现象**：最初版本的 `calculateInterest()` 是"每调用一次结算一天利息"（`余额 × 年利率 / 360`），与计划 F09"按日计息、手动结息触发"的语义不符——结息两次就计两天，且无法体现"距上次结息多少天"。
- **定位与分析**：按日计息必须有一个可持久化的起算点，否则跨天、跨会话都会算错。
- **解决过程**：给 `CurrentAccount` 增加 `lastSettleDate`（上次结息日）成员，`calcInterest(today) = 余额 × 利率/10000 × daysBetween(lastSettleDate, today) / 360`，结息后更新起算点。这带来一个文件格式问题：accounts.txt 的 12 个公共字段里没有它的位置——最终作为**第 13 个尾字段**追加（§5 已注明"各类型附加字段在后"，且老数据缺省时取开户日，向后兼容），这是本次唯一的文件格式 [contract] 变更，已与 README 同步。

#### 问题二：队友第 1 周的 core 骨架与计划红线不一致，改还是不改
- **现象**：拉取仓库后发现 `Account/Transaction` 用 `double` 存金额、`bool` 返回错误、`string` 账号，与 README §2"第 1 周定死"的三条红线相悖；而且 `Account` 用 `string` 账号、`User` 用 `long long` id，两套体系内部就不一致。
- **定位与分析**：这些头文件属于 core 域层（A 的模块所有权），现在是改动成本最低的时刻——`Bank` 还没写、`Storage.cpp` 还是空壳，没有任何代码依赖旧签名；拖到第 3 周界面接上后返工成本会翻倍。
- **解决过程**：按计划红线完成对齐（金额 `long long` 分、异常化、id 统一 `long long`、`calcInterest()` 命名），同时**保留了他合理的部分**：`AccountStatus` 枚举（比计划里的 `frozen` 布尔更丰富，直接覆盖销户语义）、`Logger` 的目录自创建逻辑、密码异或混淆方案。改动清单全部写进本周记与 README；接口变更对 B 的影响点只有"构造函数签名与序列化格式"两处，属于 [contract] 级变更，需按约定向 B 说明并征得同意。

#### 问题三：整数分计息的运算顺序与溢出
- **现象**：`余额(分) × 利率×10000 × 天数 / (10000×360)` 若先除后乘会丢精度，全乘起来又要担心 `long long` 溢出。
- **定位与分析**：估算最坏情况：余额 100 亿元 = 10¹² 分，利率 175（1.75%），天数最多 3×365+1 ≈ 1096，乘积 ≈ 1.9×10¹⁷ < 9.2×10¹⁸（`long long` 上限），安全。
- **解决过程**：确定"**先乘后除**、向下取整"的顺序并在注释里写明依据；利息不足 1 分自动舍去（银行惯例），演示中 1000.00 元存 30 天得 0.29 元与手算一致。

#### 问题四：默认实参写在了 `.cpp` 的函数定义里
- **现象**：审查队友代码时发现 `CurrentAccount` 构造函数的默认实参 `double rate = 0.003` 写在 `src/CurrentAccount.cpp` 的**定义**处而非头文件**声明**处——有的编译器接受、有的直接报"重复默认参数"或调用点看不到默认值，属于未定义行为的灰色写法。
- **解决过程**：重构时统一改为默认实参只在头文件声明处给出（`rateX10000 = 35`），`.cpp` 定义不再重复。顺带把计划 §8 要求的入口名 `console_main.cpp` 落实（原 `main.cpp` 为 Logger 临时测试占位，其功能已并入新入口的第 8 节演示）。

#### 问题五：转账的原子性
- **现象**：转账最直观的写法是"先扣款、再入账"，两步分别调用 `withdraw/deposit`——若第二步因为收款方被冻结抛异常，付款方的钱已经扣了，出现"钱在半路消失"的中间态。
- **解决过程**：`Bank::transfer` 改为**先集中完成全部前置校验**（双方存在、双方状态正常、金额合法、余额充足，任一失败双方余额都不动），校验全部通过后才执行变更；内部 `withdraw/deposit` 的重复校验此时必然通过。这一点在代码注释里显式说明，是答辩可以讲的设计点。

### 4. 心得体会

本周最大的收获是理解了"**接口契约先行**"的价值。第 1 周定下的五条设计约定（整数分、自实现 Date、Bank 门面、异常体系、密码混淆）初看只是风格偏好，这周真正写业务逻辑时才发现每一条都在消灭一类未来的 bug：整数分消灭了对账误差，异常体系消灭了"返回值被忽略"的隐患，门面模式让 UI 层永远不需要知道 `Account` 的字段长什么样。

对队友代码的重构也让我体会到"契约 vs 现实"的取舍：红线必须对齐，但对方合理的设计（状态枚举、日志的目录自愈）应该保留并吸收——代码评审的目的不是证明谁对谁错，而是让两个人的代码像一个人写的。另外转账原子性、利息起算点这两个问题都是先在纸面上推演各种失败路径才暴露出来的，"先想清楚怎么错，再动手写怎么对"比直接堆代码快得多。
