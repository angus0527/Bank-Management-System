### 2. 遇到的问题与解决过程

本周在打造高健壮性控制台交互体验与防御性编程过程中，遇到并解决了以下核心技术问题：

#### 问题一：Windows 管道重定向与隐藏 UTF-8 BOM 导致菜单选项判定失效
- **现象**：在通过脚本或特殊终端向控制台输入数字菜单选项（例如输入 `1` 或 `2`）时，程序不断打印“无效选项，请重新输入”，无法进入下一层菜单。
- **定位与分析**：在深入追踪标准输入流后发现，在 Windows 终端环境下（特别是 PowerShell 管道传递），输入流开头经常被操作系统自动注入长度为 3 字节的 UTF-8 字节序标记（BOM，即十六进制 `0xEF, 0xBB, 0xBF`），且尾部常附带 `\r\n`。读取到的实际字符串长度为 4 甚至 5，直接进行 `if (choice == "2")` 判定必定为 `false`。
- **解决过程**：编写了专用的跨平台输入清洗函数 `cleanInput(std::string s)`：利用 `while` 循环通过十六进制掩码强转判断，剥除字符串首部可能存在的所有 BOM 隐藏字节、制表符与回车换行，并同步剔除尾部空白字符。经过这道“清洗”工序后，不论是键盘敲击还是脚本管道重定向，菜单选项识别均达到 100% 精准无误。

#### 问题二：标准输入异常或遇到流末尾（EOF）时的死循环隐患
- **现象**：当用户在控制台直接按下 `Ctrl+C`、`Ctrl+Z` 或管道输入读完最后一行时，控制台瞬间无限循环刷屏输出“请选择操作：无效选项...”，CPU 占用率飙升。
- **定位与分析**：原本的读取代码简单写为 `std::cin >> choice;`。当输入流遇到 EOF（文件结束符）或发生硬件流错误时，`cin` 的状态标志位（failbit/eofbit）被置位，后续的 `cin >>` 不再阻塞读取而直接返回失败，而 `choice` 变量保留上一次的值，导致外部 `while(true)` 陷入死循环。
- **解决过程**：遵循严谨的防御性编程规范，将所有交互输入改为流状态判断保护：`if (!(std::cin >> choice)) { break; }`。一旦检测到流异常或用户强行中断输入，程序优雅跳出当前循环并触发安全存盘退出，彻底消除了流死循环崩溃风险。

#### 问题三：金额转换浮点四舍五入防坑与格式校验
- **现象**：测试时输入诸如 `100.555` 或负数、非法字符时，系统应有前置校验，而不能依赖后续类型强转崩溃。
- **定位与分析**：金额涉及银行账目的绝对精确性。若直接使用 `std::stod` 乘以 100 强转整型，浮点数底层二进制表示（如 `0.55 * 100 = 54.999999...`）容易造成截断损失 1 分钱。
- **解决过程**：编写了专用的 `parseYuanToCents` 金额转换安全函数：
  1. 通过字符分析检测小数点后数字长度，严格限制不得超过 2 位小数；
  2. 拒绝小于等于 0 的金额输入；
  3. 采用 C++11 `<cmath>` 提供的标准数学四舍五入函数 `std::llround(val * 100.0)`，彻底消除了浮点数舍入误差，坚守全系统以“分”为整数底层的铁律。

### 4. 心得体会

本周对我而言是一次极其深刻的“工程哲学思考”。在项目早期，我们往往容易陷入追求“界面华丽”的误区，花费大量时间解决 GUI 库的动态链接库冲突和系统主题兼容问题。而在本周果断做出剥离 Qt、专心打造纯 C++ 交互式控制台的决策后，整个项目的重心重新回归到了面向对象设计的本真上——清晰的多态抽象、严密的异常防御、优雅的分层设计以及健壮的数据持久化。

在打磨控制台交互的过程中，面对字符编码 BOM 污染、输入流状态机控制以及浮点金额转换这些真实细节，我体会到了“细节决定成败”的工匠精神。优秀的代码不在于外表的粉饰，而在于底层架构的纯净、逻辑的严密与对异常的从容应对。代码正式冻结的那一刻，我为我们构建的这一套健壮而优雅的银行系统感到由衷的自豪。
