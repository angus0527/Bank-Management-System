### 2. 遇到的问题与解决过程

#### 问题一：货币存储方案在 `double` 与整数“分”之间的权衡
- **现象**：最初起草需求时，曾考虑用 `double` 存储元为单位的余额，觉得写公式更直观。
- **分析与解决**：做了一个简单的测试实验：`0.1 + 0.2` 在 IEEE 754 双精度浮点下结果为 `0.30000000000000004`。在银行高频转账和按日计息场景中，这种误差不断累积会导致“销户时余额永远无法精确等于 0.0”的严重 Bug。最终决定底层统一用 `long long` 存“分”（例如 `123.45` 元存为 `12345`），仅在输入解析与终端展示时做元/分转换，从根源上消除精度隐患。

#### 问题二：客户与管理员权限边界的界定
- **现象**：讨论销户、结息、查流水等功能时，不确定哪些功能归客户、哪些归管理员。
- **分析与解决**：对照现实银行网银与柜面风控模型，清晰划分了两套权限：客户仅能操作自己名下的银行卡（查余额、存取转、开新卡、对单卡结息和销户、导出对账单）；管理员具备全行上帝视角，可查看全行账户与客户资产、执行冻结/解冻风控、一键全行日终结息以及审计系统日志，但不能越权以管理员身份开立个人储蓄卡。

### 2. 遇到的问题与解决过程

#### 问题一：多文件工程中源文件找不到 `include/` 下的头文件
- **现象**：将头文件移至 `include/`、源文件移至 `src/` 后，在 `src/` 中的 `.cpp` 文件直接写 `#include "Account.h"`，CMake 编译报错 `fatal error: Account.h: No such file or directory`。
- **分析与解决**：排查 `CMakeLists.txt` 发现未将 `include` 目录加入到编译器的头文件搜索路径中。在 `CMakeLists.txt` 中添加 `include_directories(include)` 后，所有源文件均能直接按简洁文件名引入头文件，无需到处写繁琐的相对路径 `../include/`。

#### 问题二：终端直接调用 `g++.exe` 报系统错误码 `3221225781`
- **现象**：在命令行手动测试单文件编译时，直接通过绝对路径调用 `D:\mingw64\bin\g++.exe` 导致汇编器 `as.exe` 启动异常退出。
- **分析与解决**：经排查，`g++` 编译过程中会自动派生子进程调用同目录下的 `cc1plus.exe` 和 `as.exe`，由于当前终端的 `PATH` 环境变量未包含 `D:\mingw64\bin`，子进程找不到依赖的动态库。将 `D:\mingw64\bin` 正确加入系统 `PATH` 并重启终端后，命令行编译与 CMake 构建均恢复正常。

### 2. 遇到的问题与解决过程

#### 问题一：`Bank.h` 与 `Storage.h` 之间的循环包含风险
- **现象**：最初构想时，打算在 `Bank` 类内部直接持有 `Storage` 对象完成自动保存，同时 `Storage::load(Bank&)` 又需要引用 `Bank` 类，导致两个头文件互相 `#include` 引发循环依赖编译错误。
- **分析与解决**：重新审视软件分层职责后意识到：领域对象 `Bank` 不应该关心自己怎么存盘！于是彻底移除了 `Bank` 对 `Storage` 的依赖，改由最外层主程序协同调用 `storage.load(bank)` 与 `storage.save(bank)`；同时在 `Storage.h` 中仅使用前置声明 `class Bank;`，在 `Storage.cpp` 中再包含 `Bank.h`，彻底斩断了头文件循环依赖。

#### 问题二：基类指针容器析构时的内存泄露隐患
- **现象**：在设计 `std::unique_ptr<User>` 存放 `Customer` 实例时，讨论到释放容器时是否会正确调用派生类的析构函数。
- **分析与解决**：回顾 C++ 多态内存模型，若基类析构函数非虚函数，通过基类指针删除派生类对象会触发未定义行为（`Customer` 内部的 `std::vector` 和 `std::string` 内存将发生泄露）。因此我们在 `User`、`Account` 和 `Storage` 三个基类中均严格声明了虚析构函数 `virtual ~ClassName()`，确保多态销毁安全无虞。

### 2. 遇到的问题与解决过程

#### 问题一：操作系统暗黑模式（Dark Mode）与硬编码深色冲突
- **现象**：在暗黑模式操作系统下运行程序，主界面顶部客户信息文字发灰昏暗，几乎看不清。
- **分析与解决**：代码中对标签样式进行了硬编码：`color: #212529`（深灰色）。当 Qt 继承系统暗黑底色时，深灰文字叠在深灰背景上对比度极低。移除了非必要的文字颜色硬编码，使其自适应继承系统前景色（暗黑模式下为纯白）；同时将余额高亮色由深蓝调整为高对比度的明亮浅青蓝（`#38bdf8`），状态标签改用清新薄荷绿与珊瑚红，实现了自适应暗黑模式的高对比度美化。

#### 问题二：数据重新装载时多账户聚合绑定的丢失
- **现象**：储户在线开立新账户后名下能看到新卡，但重启程序后，储户名下的银行卡下拉列表全部显示为空。
- **分析与解决**：审查 `Storage.cpp` 的 `loadAccounts` 逻辑发现：读档时仅调用了 `bank.addAccount(...)` 将账户放回银行总表，遗漏了向对应的 `Customer` 对象回填 `accountId`。在 `loadAccounts` 中，每解析一个账户后，立即通过 `bank.findUser(ownerId)` 动态向下转型为 `Customer*`，调用 `cust->addAccount(id)` 补全双向绑定，成功解决了名下卡号丢失问题。

#### 问题三：执行工作目录切换引发的存储文件定位失败
- **现象**：当直接进入 `cmake-build-debug/` 运行程序时，系统弹出“用户不存在，用户名或密码错误”，无法完成首次登录。
- **分析与解决**：程序默认以相对路径 `"data/users.txt"` 打开数据文件。当在 IDE 根目录或构建子目录不同位置启动时，当前工作目录（CWD）发生偏移，若该目录下没有预先放置 `data/` 目录，文件流打开将静默失败。在 `Storage.cpp` 中编写了智能路径解析函数 `resolvePath`：优先检查当前目录下的 `data/`，若不存在则自动向上回溯一级（`../data/`）探测。同时在启动入口处增加保底检测，若读取后用户表为空，自动初始化默认测试数据并存盘，杜绝了初次部署时的空库报错。

### 2. 遇到的问题与解决过程

#### 问题一：Windows 管道重定向与隐藏 UTF-8 BOM 导致菜单选项判定失效
- **现象**：在通过脚本或特殊终端向控制台输入数字菜单选项（例如输入 `1` 或 `2`）时，程序不断打印“无效选项，请重新输入”，无法进入下一层菜单。
- **分析与解决**：在深入追踪标准输入流后发现，在 Windows 终端环境下（特别是 PowerShell 管道传递），输入流开头经常被操作系统自动注入长度为 3 字节的 UTF-8 字节序标记（BOM，即十六进制 `0xEF, 0xBB, 0xBF`），且尾部常附带 `\r\n`。读取到的实际字符串长度为 4 甚至 5，直接进行 `if (choice == "2")` 判定必定为 `false`。
- **解决过程**：编写了专用的跨平台输入清洗函数 `cleanInput(std::string s)`：利用 `while` 循环通过十六进制掩码强转判断，剥除字符串首部可能存在的所有 BOM 隐藏字节、制表符与回车换行，并同步剔除尾部空白字符。经过这道“清洗”工序后，不论是键盘敲击还是脚本管道重定向，菜单选项识别均达到 100% 精准无误。

#### 问题二：标准输入异常或遇到流末尾（EOF）时的死循环隐患
- **现象**：当用户在控制台直接按下 `Ctrl+C`、`Ctrl+Z` 或管道输入读完最后一行时，控制台瞬间无限循环刷屏输出“请选择操作：无效选项...”，CPU 占用率飙升。
- **分析与解决**：原本的读取代码简单写为 `std::cin >> choice;`。当输入流遇到 EOF（文件结束符）或发生硬件流错误时，`cin` 的状态标志位（failbit/eofbit）被置位，后续的 `cin >>` 不再阻塞读取而直接返回失败，而 `choice` 变量保留上一次的值，导致外部 `while(true)` 陷入死循环。
- **解决过程**：遵循严谨的防御性编程规范，将所有交互输入改为流状态判断保护：`if (!(std::cin >> choice)) { break; }`。一旦检测到流异常或用户强行中断输入，程序优雅跳出当前循环并触发安全存盘退出，彻底消除了流死循环崩溃风险。

#### 问题三：金额输入精度防截断与四舍五入
- **现象**：测试时输入诸如 `100.555` 或负数、非法字符时，系统应有前置校验，而不能依赖后续类型强转崩溃。
- **分析与解决**：编写了专用的 `parseYuanToCents` 金额转换安全函数：严格限制小数点后不超过 2 位有效数字，拒绝小于等于 0 的金额输入，并采用标准数学四舍五入函数 `std::llround(val * 100.0)` 将元安全折算为 64 位整数分，坚守全系统以“分”为底层的金融安全红线。
