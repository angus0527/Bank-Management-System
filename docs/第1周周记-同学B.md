### 2. 遇到的问题与解决过程

本周在从设计图纸向实际编码推进的过程中，遇到了若干典型的编译、面向对象设计及操作系统底层问题，均已通过查阅资料与调试成功解决：

#### 问题一：静态成员函数误用 `this` 指针导致编译报错
- **现象**：在 `Logger.h` 中编写静态路径配置函数 `static void setPath(const std::string& path)` 时，随手写了 `this->path = path;`，编译器报错：`'this' is unavailable for static member functions`。
- **定位与分析**：C++ 中静态成员函数属于整个类体系，调用时不依赖具体的对象实例，因此底层没有传递隐藏的 `this` 指针。
- **解决过程**：将形参重命名为 `npath`，直接使用 `path = npath;` 完成对静态变量的赋值，编译恢复正常。

#### 问题二：派生类构造函数的参数转发与默认构造机制
- **现象**：在构思 `Customer` 和 `Admin` 类时，思考是否需要提供无参的默认构造函数。
- **定位与分析**：在金融业务模型中，银行绝不允许存在没有姓名、账号、密码的“空客户”；在 C++ 语法机制上，基类 `User` 已经定义了带参构造函数，编译器不再自动生成无参构造。若派生类强行定义无参构造，会因找不到基类的 `User()` 而报错。
- **解决过程**：派生类不设默认构造函数，统一通过成员初始化列表（Member Initializer List）将 ID、姓名、密码显式透传给基类 `User(...)`，同时初始化派生类特有成员，既符合金融现实约束，又保证了语法的严谨性。

#### 问题三：工作目录不匹配导致 `ofstream` 写入静默失败
- **现象**：在 `main.cpp` 中调用 `Logger::log()` 之后，程序正常退出（代码 0），但控制台没有任何输出，且磁盘上找不到 `logs.txt`。
- **定位与分析**：经排查，CLion 运行时工作目录默认位于 `cmake-build-debug/`，而代码中文件路径指定为相对路径 `"data/logs.txt"`。在 C++ 标准中，`std::ofstream` 仅负责创建文件，**若文件的父级目录（`data/`）在磁盘上不存在，流打开操作将静默失败（`is_open() == false`）**，导致后续读取也为空，没有抛出异常但实际未执行。
- **解决过程**：引入现代 C++17 `<filesystem>` 库，在打开流前通过 `std::filesystem::path` 提取父级路径，并调用 `std::filesystem::create_directories()` 自动递归创建缺失的目录，彻底排除了因工作目录变动导致的存盘静默失败隐患。

#### 问题四：Windows 控制台汉字编码不匹配产生乱码
- **现象**：日志被成功读出并打印到控制台时，中文显示为 `[2026-10-21 ...] 绯荤粺绠＄悊...` 乱码。
- **定位与分析**：项目源文件和保存的文本数据均采用现代标准 UTF-8 编码，而中文 Windows 操作系统的控制台终端默认采用 GBK（代码页 936）进行字符解析。终端用 GBK 编码表去翻译 UTF-8 的字节流，造成了经典乱码。
- **解决过程**：在 `main.cpp` 入口处引入 `<windows.h>`，调用 Windows API `SetConsoleOutputCP(CP_UTF8)` 将控制台活动代码页显式切换为 UTF-8（65001），成功恢复了清爽正确的中文显示。

### 4. 心得体会
在第一周的开发实践中，我体会到了“架构先行”与“面向接口设计”给大型项目带来的巨大便利。在设计 `User` 体系和 `Storage` 抽象接口时，我们先通过纯虚函数明确各个类的权责边界与交互协议，让各个模块能够高度解耦、独立推进。

同时，本周解决的几个真实 Bug 让我获益匪浅：不论是 C++ 静态成员的存储机制、构造函数的初始化时序，还是现代文件系统的目录自修复与终端编码映射，都让我深刻意识到，优秀的软件工程不仅在于写出逻辑正确的代码，更在于对操作系统底层环境、运行时边界条件和防御性编程细节的严谨把控。这些动手解决问题的经历为后续两周更复杂的系统开发打下了坚实的技术底气。
